## Phase A — Fishing at the park (5.3.15)

### A1. Capture only the tracked meter region once locked

Where: `src/Automation/FishingMeterDetector.cs` `FishingMeterService.CaptureAndAnalyze` (line 1246) captures
`new Rectangle(Point.Empty, resolved.Bounds.Size)` (line 1263) every sample. `AnalyzeFrameDetailed`
(line 1045) then clones the tracked region (line 1059) out of the full frame.

Change:

1. When `tracker?.HasLock == true`, compute `windowBounds = new Rectangle(Point.Empty, resolved.Bounds.Size)`,
   `wide = tracker.GetRegion(windowBounds, 1.10)` (covers the ±10 % rescan at lines 1136–1142), inflate by 25 %
   per side, clamp to `windowBounds`. Capture that rectangle only.
2. Add `AnalyzeTrackedCrop(Bitmap crop, Point cropOrigin, Rectangle windowBounds, FishingMeterTracker tracker)`:
   translate `tracker.GetRegion(windowBounds[, 0.90 | 1.10])` by `−cropOrigin`, run the same `Inspect` logic,
   translate the resulting `FishingMeterCandidateEvidence.Region` back by `+cropOrigin` before
   `tracker.Update(windowBounds, …)` and before returning, so every recorded `candidate.region` stays in window
   coordinates.
3. Cropped miss (meter not visible in the crop) → dispose the crop, capture the full window, run today's
   `AnalyzeFrameDetailed` unchanged. Behaviour on meter loss is therefore identical to 5.3.14 plus one small
   extra capture per missed sample. Optional: after 8 consecutive cropped misses skip the crop attempt until the
   tracker relocks (reacquire phase already samples at 40 ms).
4. `FishingMeterFrameSample` gains `Point Origin` (Point.Empty for full frames). `FishingDebugSession.RecordMeter`
   / `RecordCapture` / `SaveFrame` metadata include `origin` and the frame size already present, so cropped
   evidence PNGs are self-describing. `CaptureEvidence("meter-loss", …)` (AdaptiveRoutineEngine.cs:678) is
   unaffected.
5. Leave `FishingPromptDetector.cs:272` (prompt phase, full frame at 120 ms cadence) alone in this phase.

Tests (`tests/CuePilot.Tests/FishingMeterTests.cs`):

- New fake `IFrameSource` that records the requested `relativeRegion` and serves crops from a fixture frame.
  Assert: first sample requests the full frame; after lock, requests are ≤ 1.6× the tracked region area and the
  observation (tension/progress/confidence) equals the full-frame observation on the same fixture.
- Assert a cropped miss is followed by a full-frame request in the same call.
- Run `DaylightVideoReplayKeepsTheMeterVisibleAcrossChangingBackgrounds` (line 70) and
  `InitialPulseStateFromTheDaytimeReplayStaysLocked` (line 237) through the new path (they drive the tracker).

Expected: GDI capture at the park drops from ~27 ms toward single digits (region readback is ~24× less data;
DWM readback cost is not perfectly linear, measure it). Risk: medium — coordinate translation and evidence
metadata; the tracker's ratio math is untouched because it always receives `windowBounds`.

### A2. Deadline-paced sampling with the high-resolution timer

Where: `src/Automation/AdaptiveRoutineEngine.cs` `RegulateFishingMeter`, the two
`token.WaitHandle.WaitOne(settings.FishingSampleMilliseconds)` calls at lines 706 and 754.
Reuse `src/Automation/PickpocketSampleClock.cs` — rename the type to `HighResolutionSampleClock`
(14 references: PickpocketObserverEngine.cs:74,143; PickpocketInputController.cs:22; three test files) and
add a one-line doc that it is shared. Pickpocket behaviour unchanged.

Change: `using var sampleClock = new HighResolutionSampleClock();` next to `clock` (line 627). At loop top take
`var sampleStartMs = HighResolutionSampleClock.NowMilliseconds;` before `CaptureMeter` (line 634). Replace both
waits with `sampleClock.WaitUntil(sampleStartMs + settings.FishingSampleMilliseconds, token)`. `WaitUntil`
already yields ≥ 1 ms on overrun, so a sample after a 63 ms pulse captures immediately instead of sleeping 47 ms.

Do **not** touch line 730 (`WaitOne(decision.PulseMilliseconds)`): the tuned 35–90 ms envelope was calibrated
with the ~8 ms stretch. Correcting it is a tuning decision for the owner (see "Decisions parked").

Tests: `SlowCaptureCadenceStretchesPulsesWithinTheHardCap` (829), `HealthyCaptureCadenceKeepsTheTunedPulseEnvelope`
(849), `FailedLiveTraceNeverCommandsAnUnboundedHold` (876) must stay green. Add a timing-collection test that the
loop's sample period is ≤ `FishingSampleMilliseconds + 5` ms with a stubbed 25 ms capture (goes in the
nonparallel `Detector timing` collection).

Behavioural note to watch live: shorter Δt makes `velocity = Δtension/Δt` noisier; only positive velocity feeds
`projected` (line 969), so the risk is slightly fewer pulses when tension jitters upward. `cadenceScale` is
clamped at 1 (line 918) and `minimumRestTicks` (line 971) still spaces pulses, so the envelope is unchanged.

Expected: tap-to-read 75 → ~30 ms at the park, ~48 → ~40 ms on a healthy GPU.

## Decisions parked for the owner

1. **Pulse wait correction.** Moving line 730 to the high-resolution timer shortens real pulses by ~8 ms
   (≈ 12 %). Either re-tune `FishingMinimumPulseMilliseconds`/`Maximum` by +8 or leave as is. Not done in A.
2. **HAGS experiment.** One fishing session at the park with Hardware-accelerated GPU Scheduling off would show
   whether DXGI recovers there. Windows setting, owner's call; A3 gives the log-side answer either way.
3. **Publishing.** Phases are local builds until the owner asks to tag.

## Not planned (looked at, rejected)

- Raising engine process/thread priority: the game is GPU-bound; CPU is not the bottleneck and it could hurt the game.
- Replacing GDI with another capture API: every path reads back through the same saturated GPU queue.
- Holding a process handle in `WindowTargetService.TryCachedMatch` (line 179): measured 73 µs; not worth the change.
- `PublishReadyToRun` / Cargo `[profile.release]`: startup and binary size only; the 5.3 s launch gap is inside
  WebView2 (backlog issue 5), not in CuePilot code.

PNG fixture on every `Bitmap.Clone` (file-backed bitmaps drop their decoded pixels). On in-memory frames, the kind
the live capture produces, the same clone costs 0.13 ms. Warmed, in-memory numbers per frame:

| Path | 2560×1440 | 1920×1080 |
| --- | --- | --- |
| tracked hit (one region) | 0.3–2 ms | 0.3 ms |
| full cascade, no meter (≈10 regions) | 11–27 ms | — |
| prompt detector | 10–19 ms | 6 ms |

So the fight loop's per-sample compute is a few ms; the remaining per-sample time is capture and the deliberate
sample deadline. The live check recipe in the Phase A gate still applies.
